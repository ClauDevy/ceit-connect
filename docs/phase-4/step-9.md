# Step 9 — Task comments without Phase 5 notifications

**Status:** Required, merged, and live on Dev and Prod. All five Step 9-DB SQL test pastes and the Step 9-UI manual verification passed (owner-confirmed).

- Add deny-by-default `task_comments` with a 4,000-character whitespace-trimmed body, Heads-Up state, at most 20 unique validated mention ids, server-derived author, creation time, and nullable edit time. Render the Collaboration & Activity thread and chip-based mention picker on the existing task detail page, never a modal.
- Anyone whose current `task_content_access()` result is `real` may read or comment. Hidden, masked, unknown-task, inactive, and profile-less callers receive the same `CCC01` error from both comment readers; zero rows means only that an authorized thread is empty. An author may edit their own comment, which re-validates the body and unordered mention set and sets `edited_at` only after a real change. An author may delete their own comment; an active Admin may delete any currently accessible comment. Co-Admins receive no blanket edit/delete right.
- Comment reads use a 25-row default and 50-row maximum keyset page. Cursor timestamp and id are both present or both absent. Each row contains safe author fields and every stored mention as only `{id, full_name}`. The mention-candidate reader accepts a name search and returns at most 20 active profiles with current real task access as only `id`, `full_name`, and `avatar_url`, regardless of the caller's role or committee. This safe profile field set matches what the existing `users` SELECT policy exposes when a row is otherwise visible.
- Archived comments remain readable to current real-content viewers, including archive-only viewers from Step 7B, but every insert/update/delete is blocked by an independent parent-status guard. Heads Up and mentions are stored for future notification generation; Phase 4 creates no notifications and changes no unread counts.
- **Database impact:** migrations `20261023120000_task_content_access_for_user.sql` and `20261023130000_task_comments.sql` add one internal user-aware access helper, preserve `task_content_access(uuid)` as an ungranted wrapper with identical attributes and behavior, add the comment table/indexes/guard, and expose only fixed-shape readers plus three narrow writers. Raw task/user RLS and the existing direct-task-writer inventory remain unchanged.
- **Write design:** authenticated clients have no direct comment-table privileges or policies. `add_task_comment`, `edit_task_comment`, and `delete_task_comment` derive/re-read security state and mutate only `task_comments`. Before any row lock, add checks current real access to the supplied task; edit/delete first read only the comment's task id without a lock, return `CCC01` if it is missing, and perform the same access check. Masked, hidden, and unknown callers therefore take no task/event/comment lock and receive the same `CCC01`. Authorized writers then preserve the existing parent task `FOR NO KEY UPDATE`, stored parent event `FOR SHARE`, post-lock relationship/access/status re-check, and Archived rejection. The trigger independently repeats the lifecycle guard and permits only the nested cascade reached after an approved parent-task deletion.
- **Concurrency:** comment writes share the task-then-event order already used by `task_work_links_guard_writes` and Step 8 child writers. They cannot deadlock with task-first claim/volunteer/work-link operations on the same task because the task lock serializes them. They may meet the accepted inverse order of event-first `edit_event_with_tasks`/`delete_task`; PostgreSQL resolves that race with `40P01`. `archive_event` never waits on task rows, so it cannot complete a cycle: a waiting comment writer wakes, re-reads `Archived`, and fails. Relationship changes detected after locking use `40001`. The future UI treats both `40001` and `40P01` as retryable and refetches before asking the user to try again.
- **Guards that must remain true:** every comment read/write uses the current real-content decision; confidential existence never leaks through comment/mention lookup differences; Archived comments are immutable; every role may mention any active target whose `task_content_access_for_user(task, target)` result is `real`, without applying the caller's raw `users` row-visibility scope; comment operations cannot mutate tasks/events or affect the Active-event task invariant.
- **Error family:** `CCC01` unavailable/not-real, `CCC02` invalid reader input, `CCC03` invalid body/Heads-Up value, `CCC04` invalid mentions, `CCC05` Archived read-only, `CCC06` edit forbidden, `CCC07` delete forbidden, `CCC08` stale edit, `CCC09` no-op edit, and `CCC10` immutable comment integrity. `40001` and `40P01` remain retryable concurrency errors rather than business errors.
- **Test deliverable:** `docs/PHASE-4-STEP-9-TESTS.md` follows the global test contract with five self-contained DEV pastes and expected result counts `23 / 15 / 19 / 19 / 20`. It covers helper parity and removal, catalogs/grants, every role/access/lifecycle, authorization-before-lock ordering, author edit/delete, Admin deletion, Co-Admin limits, trimming/caps, `edited_at`, unordered mention no-op detection, all-role mention eligibility plus masked/inactive/unknown rejection, current-access revocation, pagination, Archived immutability, cascades, lock order, Step 7B compatibility, and absence of notification/activity writes.
- **Acceptance:** every current real-content viewer can read and comment; masked/hidden/inactive users receive non-leaking `CCC01`; authors edit/delete their own comments; active Admin deletes any accessible comment; edited comments show “(edited)” in Step 9-UI; access changes apply immediately; Archived comments are readable but immutable; no notification row is created.
