# Step 5a — Columns, safe backfill, and dependency integrity

**Status:** Gate-critical.

- Add immutable `tasks.created_by uuid → users.id` and `tasks.sort_order bigint`. Backfill creator from `events.created_by` as historical provenance only. Backfill order deterministically within event/phase/status from `created_at, id`; then make both non-null and add required indexes/constraints.
- Supabase CLI normally wraps each migration file in one transaction unless the file opts out with `-- pg-delta: transaction=false`; this migration must not opt out. Do not rely on the runner alone: put trigger disable, both backfill updates, trigger re-enable, and immediate `pg_trigger` assertions inside one atomic `DO` statement. If a nonstandard runner does not wrap the file, failure of that statement still rolls back its trigger changes and data writes together; later-file failure cannot leave a disabled trigger.
- In that critical section, resolve/name each current trigger explicitly and disable only `tasks_guard_archived_event_writes`, the assignee guard, and task activity-log trigger—never `DISABLE TRIGGER USER/ALL`. Update only the two new columns, re-enable each trigger, and assert each is attached/enabled. This permits one-time Archived metadata backfill without assignee rejection or activity spam and creates no application write window.
- Update every task-creation path to derive `created_by = auth.uid()` and server-side initial order. Any replacement of `create_event_with_tasks` or `edit_event_with_tasks` retains its exact signature, security mode, lifecycle checks, grants/revokes, and behavior; require function-body diff and `pg_proc` signature/count proof with no overload.
- Keep one `depends_on_task_id`. Validate no self-dependency, same event, and no cycle. Block deletion of a referenced prerequisite clearly. Blocked state stays derived and changes never alter status automatically.
- Reject task reparenting. Current raw update RLS plus the leadership bypass in the assignee guard permits an Admin/owning Co-Admin to change `event_id`; add an independent non-client-callable `SECURITY INVOKER RETURNS trigger` function with fixed empty `search_path` on `BEFORE UPDATE OF event_id` that rejects every real `old.event_id IS DISTINCT FROM new.event_id` change. A no-op same-id assignment is harmless. Keep the existing deferred event-move Active-invariant trigger attached as defense in depth. No Phase 4 RPC may update a stored task's `event_id`.
- **Database impact:** alters `tasks.created_by`, `tasks.sort_order`, validation around `depends_on_task_id`, and adds task-event immutability; updates existing creation/edit RPCs only as required. New migration: **yes**. Raw task RLS stays unchanged.
- **Guards that must remain true:** disabled triggers are re-enabled before the atomic block succeeds; Archived rows change only in the two backfill columns; event/task lifecycle guards and Active-event triggers survive; `tasks.event_id` is immutable through raw SQL and RPCs.
- **Security risks:** trigger names or restoration mistakes are dangerous, so fail closed with catalog assertions. Never use creator for authorization. Never trust caller event ids for cycles. Keep replacements exact with no overload. Row-level update permission is not column immutability.
- **Test deliverable:** `docs/PHASE-4-STEP-5A-TESTS.md` follows the global contract and verifies deterministic backfill, atomic trigger restoration under forced failure, attached/enabled guards, zero activity noise, creator immutability/non-authorization, exact RPC signatures, dependency integrity/protected prerequisites, and deferred constraints with `set constraints all immediate`. Direct `UPDATE tasks SET event_id = ...` tests cover Admin, owning/other Co-Admin, assigned Member, and no-op same-id behavior; function-body checks prove event/edit/move/narrow RPCs do not update task `event_id`.
- **Acceptance:** all existing task lifecycles receive deterministic creator/order values without activity spam; guards are attached afterward even under failure simulation; new tasks derive creator/order; creator/order forgery, invalid dependency/deletion, and all real reparenting fail; Phase 3 RPC and invariant tests still pass.
