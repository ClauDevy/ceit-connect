# Step 1 — Transactional archive RPC

**Status:** Gate-critical. **Prerequisite:** urgent Step 1A hotfix.

- Replace the route's direct `events` update with one database RPC that takes an exclusive lock on the target event row, verifies an active Admin caller and current `Active` state, re-counts incomplete tasks inside the same transaction and lock, compares the exact count and event version with confirmation state, and archives atomically. Incomplete tasks warn but never block; use the exact count.
- Keep the route POST-only. Runtime-validate event UUID, expected incomplete count, and expected version; use the caller's session, not service role; check the RPC error; map not-found/stale/already-archived failures clearly. A changed count requires refresh and reconfirmation.
- Make archive serialization a database contract. Every task/task-child lifecycle guard trigger takes `SELECT ... FOR SHARE` on the stored parent `events` row and only then re-reads status. This includes guards covering raw task insert/update/delete and the move, claim, assign, delete, unassign, dependency, confidentiality, work-link, and comment paths as they are introduced. The archive RPC holds the conflicting exclusive event-row lock across its recount and status change, so a guard that waits for archive resumes, re-reads `Archived`, and rejects the write.
- Do not claim a universal event-first lock order for raw writes: PostgreSQL raw task `UPDATE`/`DELETE` locks the task row before its `BEFORE ROW` trigger can acquire the event lock. Keep those raw paths because Edit Event and existing RLS depend on them. The archive RPC never locks or waits on task/task-child rows—it locks only the event before its ordinary count read—so it cannot form a task-row/event-row deadlock with those writers. A narrow task-row RPC with a known stored parent may acquire the event lock before task rows as an optimization; task-child mutators follow the task-first resolution order below. Every guard derives parentage from stored relationships rather than trusting a client event id.
- State the parent-reference boundary explicitly. The current `tasks_update` policy and constraints do not make `tasks.event_id` immutable for Admin/owning-Co-Admin updates; its foreign key validates only that the destination event exists. Step 5a later adds the unconditional task-reparent rejection. Until that lands, an `UPDATE` that changes `event_id` must have the lifecycle guard collect the distinct old and new event ids, lock both event rows in one deterministic id order, and only then re-read and validate both statuses. This prevents moving a task out of or into an Archived event and serializes with an archive of either parent.
- A task-child foreign key does not make its `task_id` immutable either. Each Phase 4 child schema must enforce immutability with no `UPDATE` policy/path for that column or an explicit column guard. For every child insert/update/delete—and especially any path that can change `task_id`—the lifecycle guard first locks all distinct task rows referenced by `OLD` and `NEW` in deterministic task-id order. Only after those locks are held may it read their stored `event_id` values, lock all distinct parent event rows in deterministic event-id order, and re-validate both the child-to-task relationships and parent statuses. This prevents a concurrent task reparent from changing which events the child guard must protect. Never rely on client-supplied parent ids or sequential caller-ordered locks.
- **Database impact:** reads/updates `events.status` and `events.updated_at`; reads `tasks.event_id/status`; updates current lifecycle guard functions as needed to acquire the parent shared lock before their status checks. New migration: **yes**, for the restricted RPC, guard changes, and grants/revokes. Do not broaden `events_update` or task policies.
- **Guards that must remain true:** only Active → Archived; Archived event/task rows remain immutable; no task update/delete occurs, so the Active-event invariant remains intact; confidential content is never returned.
- **Security risks:** never trust client count, status, role, version, or parent id. Lock and re-read them; preserve RLS/triggers; check every result; use no service-role bypass. An omitted shared lock or status re-read can create a stale archive count. A foreign key is not column immutability, and locking old/new parents sequentially in caller-chosen order can deadlock reciprocal changes. Do not “fix” the unavoidable raw-write lock order by removing raw policies or Edit Event paths.
- **Test deliverable:** `docs/PHASE-4-STEP-1-TESTS.md` follows the global contract and covers exact-count warnings, stale versions/counts, concurrent double submission, all statuses/roles, unchanged archive/task guards, and catalog/function-body checks for the shared parent lock followed by the status re-read. Add a two-session archive-versus-task-write test: prove the task write either commits before archive and is included in the locked recount, or waits on the archive event lock, resumes afterward, re-reads `Archived`, and fails. Also prove archive never waits for the writer's task-row lock. Before Step 5a, test task reparenting against archive on both the old and destination event and assert deterministic two-parent locking plus rejection if either is Archived; after Step 5a, re-run it as an unconditional reparent denial. For every selected task-child table, assert direct `task_id` changes are denied and verify the guard's deterministic task-lock → stored-event lookup → deterministic event-lock → relationship/status revalidation sequence. If any approved path can change that reference, add concurrent task-reparent, old/destination-event archive-race, and reciprocal-order tests. The archive count must never go stale.
- **Acceptance:** only an active Admin archives; warning count is exact; stale confirmation fails; reconfirmation archives one Active event; concurrent task/task-child writes and any permitted parent-reference change serialize with every affected event; archive does not deadlock on task-row locks; incomplete tasks freeze as stored; direct Archived writes still fail; final Phase 4 task and task-child parent references are immutable; raw Edit Event/RLS paths remain available for their approved non-parent writes on non-Archived events.
