# Step 1A — Raw tasks read hardening

**Status:** Gate-critical, urgent standalone hotfix. Build and deploy this before Step 1 or any other Phase 4 work because the `request_backup` and inactive-assignee raw-read leaks are live on Prod.

- Replace `tasks_select` under the same policy name. Require one explicit active-profile check around every branch. Preserve only these legitimate raw-row paths: active Admin; active owning-committee Co-Admin; active primary/assist assignee when the parent is not Draft; and any active user reading a non-confidential Archived task. Remove `request_backup = true` completely—Help Wanted will use Step 8's restricted RPC, and until then no backup request creates raw task visibility.
- The final migration already defines `my_role()` and `my_committee_id()` with `users.is_active = true`, so inactive Admin/Co-Admin role branches currently fail closed. Do not regress that behavior. The current assignee and `request_backup` branches do not call those helpers, so a deactivated assignee can still pass and any authenticated caller—including one without a profile—can pass a non-Draft backup row. Reuse a suitable active-user helper or add one fixed-empty-`search_path` boolean helper; revoke execute from `PUBLIC`/`anon`, grant only to `authenticated`, and make every branch depend on it.
- Confidential raw rows remain selectable only by an active Admin, active owning Co-Admin, or active primary/assist assignee under the lifecycle rules above. `allowed_viewers` and optional `archived_task_viewers` grantees receive real content only through the restricted detail/content RPCs in Steps 3 and 7B; they never gain raw `SELECT`.
- Replace `tasks_update` under the same name with its existing legitimate paths and column guard plus the same top-level active-profile requirement in `USING` and `WITH CHECK`. Replace `tasks_delete` under the same name with unchanged Admin/owning-Co-Admin scope plus the explicit active-profile gate. Do not broaden either policy or change `tasks_insert` here.
- Current migrations have no column-level `SELECT` restriction on `public.tasks`. Current raw callers need:
  - Archives: `id, event_id, phase, status, priority, task_type, due_date, primary_assignees, assist_assignees, created_at`.
  - Event Edit: `id, event_id, committee_id, phase, status, priority, task_type, due_date, call_time, end_time, primary_assignees, created_at`; title/description already come from `get_task()`.
  - Home incomplete count: `id, event_id, status`.
  - `edit_event_with_tasks` (`SECURITY INVOKER`): `id, event_id, committee_id, status`, plus existing insert/update/delete privileges.
  - `get_archived_event_template` (`SECURITY INVOKER`): `id, event_id, is_confidential, committee_id, title, description, phase, task_type, priority, due_date, call_time, end_time, created_at`.
  - Activity-log policies/helpers: `id, event_id, committee_id, primary_assignees, assist_assignees, request_backup, is_confidential`.
  - Security-definer content/lifecycle helpers use owner privileges and do not justify client column grants, but still need regression coverage.
- **Column-grant decision:** retain policy-only hardening. Revoking table `SELECT` and granting a safe list cannot exclude title/description without breaking the invoker-security archive-template import; converting that mature RPC solely for column grants expands this urgent fix. The residual risk is guarded by permanent direct-`SELECT` regression tests.
- Replace in place: exactly one policy each named `tasks_select`, `tasks_update`, and `tasks_delete`; any active-user helper has one zero-argument signature and no overload. Assert `pg_policies` definitions/counts and `pg_proc` identity arguments, security mode, owner, fixed `search_path`, and execute grants/revokes.
- **Database impact:** replaces `tasks_select`, `tasks_update`, and `tasks_delete`; may add one active-user helper. No columns or legitimate role scopes change. New migration: **yes**. `request_backup` remains stored but grants no raw read.
- **Guards that must remain true:** Draft tasks remain leadership-only; non-confidential Archived rows remain visible to every active user; confidential raw reads are limited to the three approved paths; inactive/missing-profile callers receive no task rows and cannot update/delete; archive freeze, assignee column guard, activity-log visibility, `get_task()`, event RPCs, and Active-event invariant remain intact.
- **Security risks:** policy precedence, a missing top-level active check, or retaining the backup branch preserves the leak. Column-grant experiments can silently break pages or invoker RPCs. Test direct SQL, catalog definitions, grants, and every existing caller; check errors rather than treating empty/partial data as success.
- **Test deliverable:** `docs/PHASE-4-STEP-1A-TESTS.md` follows the global contract. Its first rollback-safe block reproduces the current leak: an unassigned Member directly selects `title, description` from a confidential non-Draft task with `request_backup = true`. Post-fix blocks directly `SELECT` from `public.tasks` as every required role, inactive former assignee/Admin/Co-Admin, and an authenticated UUID without a profile; they also test raw update/delete activity gates, every retained/removed path, policy/helper catalogs, and every caller above.
- **Acceptance:** the pre-fix reproduction leaks exactly as documented; afterward only the approved active paths can raw-read confidential rows, active users can raw-read non-confidential Archived rows, backup/allowed-viewer/late-share status alone grants no raw access, inactive/profile-less callers receive nothing, existing callers work, and no duplicate policy/helper exists.
