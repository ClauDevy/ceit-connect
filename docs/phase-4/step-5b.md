# Step 5b — Transactional task-move RPC

**Status:** Gate-critical.

- Add one narrow `SECURITY DEFINER` move RPC owned by the existing migration owner role, like `get_task()`. Give it a fixed empty `search_path`, revoke execute from `PUBLIC`/`anon`, grant only to `authenticated`, derive identity from `auth.uid()`, and explicitly require the caller's current active role. It accepts movement intent—not final rank—locks/re-reads task, parent, dependency, and lane rows, then writes only `status` and `sort_order`. The default path creates no role and requires no new `BYPASSRLS` role.
- Permissions: Admin moves any task; Co-Admin only own committee; primary/assist assignee changes only status and is placed at destination tail; assignees cannot reorder; unassigned Members cannot move. Assignees may move backward. An incomplete dependency blocks only forward movement and never auto-reverts.
- Replace the assignee-guard function as `SECURITY INVOKER` and add one explicit `current_user = <migration_owner>` branch. In this step that branch permits only `status`/`sort_order` differences after the RPC's caller checks; direct authenticated calls remain status-only and cannot forge order. The independent archive guard is never exempted. Assert the migration owner and guard definition rather than trusting default ownership.
- **Fallback only:** if the migration-owner design cannot pass the complete privilege/guard/direct-SQL suite, use a dedicated minimal `NOLOGIN` move owner. The hosted managed `postgres` role used to apply migrations can create `BYPASSRLS` roles, but grant that attribute only if the fallback needs it. Grant no membership to gateway/service roles, remove PostgreSQL 16+ creator self-membership, assert no direct/transitive `pg_auth_members` path, require false `pg_has_role(..., 'MEMBER'/'USAGE')` for `anon`/`authenticated`/`authenticator`, and prove `SET ROLE` fails from `anon` and `authenticated`. Do not adopt the fallback merely for theoretical isolation.
- Use spaced integer ranks and deterministic transactional rebalance. Treat client neighbors/index as hints; verify same event/phase/destination and freshness. Serialize conflicts with row/advisory locks and return retryable conflicts when needed.
- For a same-lane reorder, the client retains the moved task's previous neighbor ids for the short Undo window. Undo calls this same move RPC with those previous neighbors as placement hints; the server re-validates their event, phase, status lane, adjacency, and current ordering context before choosing the rank. If the task originally sat first or last, a missing previous or next neighbor represents that boundary rather than an invalid hint, but the remaining neighbor must still be the current first or last task respectively. Normal caller, archive, dependency, permission, and conflict checks still apply; hints are never authoritative and the old rank is never forced.
- Pure rank changes create no activity entry. A status/order move creates one attributable status event; neighbor rebalance produces no business activity spam.
- **Database impact:** updates only `tasks.status/sort_order`; narrowly adjusts assignee/activity triggers. New migration: **yes**. Raw `tasks_update` remains committee-scoped.
- **Guards that must remain true:** Archived moves fail; `event_id`, phase, dependency, assignees, and content cannot change; no insert/delete or Active-event invariant break.
- **Security risks:** migration-owner definer privilege or a broad trigger exemption can become a general bypass. Restrict signature, grants, caller checks, allowed columns, and row counts; schema-qualify everything; inspect every existing migration-owner definer that can touch tasks; re-read ids; test direct forgery and concurrency.
- **Test deliverable:** `docs/PHASE-4-STEP-5B-TESTS.md` follows the global contract and covers all roles, dependency directions, assignee tail placement, Admin/own-Co-Admin reorder, other-Co-Admin denial, exact owner/security/search-path/grants, the single guard exemption and allowed column diff, direct rank/event-id forgery, Archived denial, activity noise, concurrent/stale moves, and same-lane Undo using valid, moved, removed, cross-lane, and forged previous-neighbor hints. Include successful Undo to the first position with a missing previous neighbor and to the last position with a missing next neighbor, plus rejection when the remaining neighbor is no longer at that asserted boundary. If fallback is used, add all owner-membership and failed-`SET ROLE` blocks, each ending in `ROLLBACK`.
- **Acceptance:** permission matrix holds in RPC and direct SQL; order is deterministic; assignees move backward but never reorder; dependency gates only forward; Archived/event-id writes fail; rank-only changes are quiet and status moves log once; same-lane Undo uses revalidated previous-neighbor or boundary hints, restores valid first/last positions, and fails safely when stale; default migration-owner design passes, or the documented fallback is justified by a failing test and then passes the expanded suite.
