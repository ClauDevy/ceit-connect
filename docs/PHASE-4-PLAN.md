# Phase 4 — Task engine, Kanban, dependencies, confidentiality UI: build plan

Goal: turn the Phase 3 task rows into a real Supabase-backed event board and task modal, **one step at a time**, while preserving the permanent archive freeze, confidential-content boundary, and Active-event-must-have-a-task invariant. Each step: own branch → build → manual test → `npm run build` → `npm run lint` → CodeRabbit → PR. Do not start the next step until the owner confirms the current one works. Design sources are `docs/prototypes/event.html` for the event Kanban/backlog, `docs/prototypes/tasks.html` for the task detail modal, Workspace, and Help Wanted behavior, and the task-related sections of `docs/prototypes/dashboard.html`; search only the relevant sections because these files are large.

Security reminders that apply to every step: RLS and database guards are the real enforcement; pages call `requireUser()` and mutation routes/RPCs re-check that the caller is active; confidential title/description always come through a restricted RPC, never a raw `tasks` select; security-relevant ids and fields are derived or re-read server-side; every Supabase result checks `error`; every request body is runtime-validated; every client mutation uses `try/catch/finally` and rolls back optimistic UI on failure. No Phase 4 change may make an Archived event or its task row writable.

Phase 4 does **not** include notifications, Supabase Realtime for tasks, or Executive Dashboard data wiring. The dashboard prototype is a visual/reference check only; its statistics, deadline feed, workload chart, and role-scoped route belong to Phase 5.

## Approved decisions and existing schema

- `tasks.status` already stores `To Do | In Progress | Completed`, and `tasks.depends_on_task_id` already stores the one direct dependency Phase 4 needs. There is no stored blocked flag: `blocked` remains derived from a non-Completed dependency. The lock prevents only a forward status move; it never auto-reverts a dependent task whose prerequisite later moves backward. A prerequisite with dependents cannot be deleted.
- `tasks` has no ordering column. Step 5a adds `sort_order bigint`, and Step 5b adds the only RPC that may persist board ordering.
- On an Active event, every active user sees every non-confidential task through a restricted board RPC, including its card fields, committee, and safe assignee names/avatars. Raw `tasks_select` is not broadened. Draft tasks remain hidden from Members.
- A caller without real access to a confidential task sees an opaque card/modal labelled only **“Confidential Task”** in its real status lane or Backlog. That placement necessarily reveals status and whether it is unassigned; no priority, deadline, committee, assignee, description, dependency name, comments, work links, or access list is returned.
- `tasks.created_by` is provenance only. Step 5a backfills it from the parent event creator because no better historical source exists, but neither a current nor backfilled value grants assignment, volunteer-acceptance, deletion, or any other permission.
- General task editing remains committee-scoped through `edit_event_with_tasks`: Admins may edit all tasks and Co-Admins may generally edit only their own committee. Cross-committee Co-Admin exceptions use narrow functions that change exactly one approved concern; raw task policies stay committee-scoped.

## Test-document contract for every step

Every step ships its own `docs/PHASE-4-STEP-N-TESTS.md` (lettered steps use names such as `PHASE-4-STEP-5A-TESTS.md`). Each file must be independently paste-and-run, must not depend on rows left by another test file, and must contain SQL blocks that impersonate: Admin, owning-committee Co-Admin, other-committee Co-Admin, assigned Member, unassigned Member, allowed viewer, and inactive user. Every block ends in `ROLLBACK`, including expected-failure blocks. When a test relies on a deferred constraint trigger, it explicitly runs `set constraints all immediate` before treating the mutation as accepted or rejected. UI/manual checks may follow the SQL blocks, but never replace role-impersonated database checks.

## Step 1 — Transactional archive RPC [Gate-critical]

- Replace the route's direct `events` update with one database RPC that locks the target event, verifies the caller is an active Admin, verifies the row is still `Active`, re-counts incomplete tasks inside the same transaction, compares that exact count and the event version with the confirmation state, and changes the event to `Archived` atomically. Incomplete tasks only produce the permanent-action warning; they never block archiving.
- Keep the route POST-only, validate the event UUID, expected incomplete count, and expected version at runtime, use the caller's Supabase session rather than service role, check the RPC error, and map expected not-found/stale/already-archived failures to clear responses. If the count changed, refresh the confirmation with the new exact count rather than archiving a state the Admin did not confirm.
- **Database impact:** reads/updates `events.status` and `events.updated_at`; reads `tasks.event_id` and `tasks.status`. New migration: **yes**, for the restricted archive RPC and grants/revokes. RLS policies: do not broaden `events_update` or any task policy; preserve the active-Admin-only rule and existing lifecycle/freeze triggers.
- **Guards that must remain true:** only Active → Archived is possible; Archived event/task rows remain immutable; the RPC does not update/delete tasks, so the Active-event task invariant remains intact; confidential task content is never read or returned.
- **Security risks:** never treat the client count, event status, role, or version as authoritative; lock and re-read them. RLS/trigger enforcement stays effective, every database result is checked, and no service-role bypass is needed.
- **Test deliverable:** `docs/PHASE-4-STEP-1-TESTS.md` follows the test-document contract and covers exact-count warnings, stale versions/counts, concurrent double submission, all event statuses, all roles, and unchanged archive/task guards.
- **Acceptance:** only an active Admin can archive; the warning shows the exact incomplete count; a stale confirmation is rejected; refresh and reconfirm archives exactly one Active event; incomplete tasks freeze exactly as stored; direct writes still cannot mutate the Archived event or its tasks.

## Step 2 — Read-only event Kanban [Gate-critical, visible early]

- Add the Active-event board at `/events/[eventId]`, linked from Home. Match the relevant `event.html` sections: event header, phase tabs, `TO DO / IN PROGRESS / COMPLETED` lanes, Backlog count/drawer, priority filter, loading/empty/error states, and responsive horizontal/mobile behavior. This step is read-only—no drag-and-drop or task mutations yet.
- Add an Admin-only committee filter. Co-Admins and Members receive no cross-committee filter control; filtering is UI state over only the already-authorized board response.
- Add one narrowly scoped, fixed-shape board-list RPC for active callers. For an Active event, it returns all non-confidential cards to every active user with safe committee and assignee name/avatar data. Confidential real fields are returned only to an Admin, owning Co-Admin, primary/assist assignee, or `allowed_viewers` member; everyone else receives only the id needed to open the masked shell, the real phase/status placement, and whether it belongs in Backlog. Do not fetch raw titles and mask them in React, and do not broaden `tasks_select` or `users` RLS.
- Display effective priority without rewriting the stored base value: due within 24 hours is at least High; overdue is Critical with the prototype treatment. Use one shared, tested calculation and a defined timestamp source so server/client rendering cannot disagree.
- Keep boards fresh across users with refetch-on-window-focus plus short polling while the page is visible. Pause polling in a hidden tab and after unmount. Supabase Realtime for tasks is explicitly deferred beyond Phase 4.
- **Database impact:** reads `events`; reads the board-safe subset of `tasks`; reads only `users.id, full_name, avatar_url` needed for visible assignees. No columns change. New migration: **yes**, for the restricted board-list RPC and execute grants. RLS policies: unchanged; the RPC owns the intentional Active-event board disclosure.
- **Guards that must remain true:** Draft tasks stay invisible to Members; Archived events continue to use the read-only archive route; the RPC never writes and cannot affect the Active-event task invariant; confidential fields are never returned to a masked caller.
- **Security risks:** a `SECURITY DEFINER` listing function can become a bulk data leak. Fix `search_path`, revoke public execution, require an active caller and visible Active event, return a fixed safe shape, and never build authorization from client text. Check the RPC and profile/assignee lookup errors before rendering partial results.
- **Test deliverable:** `docs/PHASE-4-STEP-2-TESTS.md` follows the test-document contract and proves Active-event all-user visibility, Draft exclusion, confidential shell shape, assignee-profile minimization, Admin-only filtering inputs, inactive-user denial, and unchanged raw-table policies.
- **Acceptance:** every active role sees all non-confidential Active-event cards and safe assignee/committee data; a masked confidential card contains only “Confidential Task” in its real lane/Backlog; Admin filtering works; priority boundaries are correct; another user's change appears after focus/refetch or the polling interval without Realtime.

Mutation controls remain hidden or disabled in this step.

The lock applies only when attempting a forward move; no database or UI process auto-reverts a dependent if its prerequisite later stops being Completed.
- Make the current confidential-access rule explicit in the response: on Draft/Active events, real content is visible to Admin, the task's owning Co-Admin, primary/assist assignees, and `tasks.allowed_viewers`. Archived confidential tasks retain those same paths under the current policies; the optional Step 7B later adds a separate archive-only viewer path.
- Show the access list only to callers who already see real task content. Comments and work links must use the current access decision on every read, so removing a user from `allowed_viewers` removes those reads immediately; a masked caller never receives their rows.
- **Database impact:** reads `events`, `tasks`, and safe assignee/viewer profile fields from `users`. No columns change. New migration: **yes**, for the restricted task-detail/assignee RPC and shared fixed-search-path content-access helper if needed. RLS policies: no raw `tasks`/`users` broadening; preserve or strictly replace `get_task()`'s authorization boundary.
- **Guards that must remain true:** Draft tasks are unavailable to Members; Archived task rows remain frozen; the modal writes nothing and cannot affect the Active-event invariant; masked board/modal output is identical.
- **Security risks:** fetching full rows and hiding fields client-side is forbidden. Do not expose emails, roles, Discord ids, allowlist UUIDs, hidden dependency titles, comments, work links, or inactive-user details through convenience joins. Avoid duplicating subtly different confidential-access logic across functions.
- **Test deliverable:** `docs/PHASE-4-STEP-3-TESTS.md` follows the test-document contract and proves real versus masked detail shapes, current-access revocation behavior, dependency-title masking, Draft/Archived behavior, and every required role.
- **Acceptance:** authorized users see real content and the current access list; an unassigned unauthorized Member gets only the opaque shell on board and modal; removing an allowed viewer immediately removes real task/comment/work-link access; a blocked task names its prerequisite only when the caller may see that name.

## Step 5a — Columns, safe backfill, and dependency integrity [Gate-critical]

- Add immutable `tasks.created_by uuid → users.id` and `tasks.sort_order bigint`. Backfill `created_by` from `events.created_by` as historical provenance only. Backfill `sort_order` deterministically within each event/phase/status lane from `created_at, id`, then make both columns non-null and add the required indexes/constraints.
- The backfill must not weaken production guards or manufacture business activity. In the single transactional migration, resolve and name each current trigger explicitly, then disable only `tasks_guard_archived_event_writes`, the assignee-guard trigger, and the task activity-log trigger—never `DISABLE TRIGGER USER/ALL`; perform updates limited to the two new columns; re-enable every trigger before the transaction can commit; then assert through `pg_trigger` that each expected trigger is attached to `public.tasks` and enabled. Any failed assertion aborts and rolls back the whole migration, so there is no state where guards stay disabled. This permits the one-time Archived-row metadata backfill, avoids assignee-guard rejection, and prevents a flood of misleading activity-log rows without allowing an application write window.
- Update every task-creation path to derive `created_by = auth.uid()` and choose the initial server-side order. If `create_event_with_tasks` or `edit_event_with_tasks` must be replaced, retain its exact argument signature, security mode, lifecycle checks, grants/revokes, and existing behavior; include a function-body diff review plus a `pg_proc` signature/count assertion proving the old function was replaced and no overload exists.
- Keep one `depends_on_task_id`. Add database validation that the prerequisite is not self, belongs to the same event, and cannot create a cycle. Block deletion of a task referenced by any dependent with a clear error. Blocked state remains derived, and dependency changes never auto-change either task's status.
- **Database impact:** alters `tasks.created_by`, `tasks.sort_order`, and validation around existing `tasks.depends_on_task_id`; updates existing creation/edit RPC bodies only as required for the new columns. New migration: **yes**. Raw task RLS stays unchanged.
- **Guards that must remain true:** all three temporarily disabled triggers are reattached/enabled before commit; Archived rows change only in the migration's two provenance/order columns and are frozen again atomically; Active-event count enforcement and all existing event/task lifecycle checks survive function replacement.
- **Security risks:** trigger disabling is dangerous if names are wrong or re-enable is omitted, so the migration must be one transaction with catalog assertions. `created_by` must never enter authorization logic. Cycle checks must not trust a caller-supplied event id, and no replacement function overload may remain callable.
- **Test deliverable:** `docs/PHASE-4-STEP-5A-TESTS.md` follows the test-document contract and verifies deterministic backfill, trigger attachment/enabled state, zero backfill activity noise, creator immutability/non-authorization, exact RPC signatures/no overloads, same-event/no-self/no-cycle dependencies, protected prerequisites, and deferred constraints with `set constraints all immediate`.
- **Acceptance:** existing Draft/Active/Archived tasks receive deterministic creator/order values without activity-log spam; all guards are verifiably attached afterward; new tasks derive creator/order; direct creator/order forgery fails; invalid dependencies and deleting a prerequisite fail clearly; all Phase 3 RPC and invariant tests still pass.

## Step 5b — Transactional task-move RPC [Gate-critical]

- Add one `SECURITY DEFINER` move RPC with fixed empty `search_path`, public execute revoked, and authenticated execute explicitly granted. It accepts movement intent—not a final rank—locks/re-reads the task, parent event, dependency, and relevant lane rows, then writes only `tasks.status` and `tasks.sort_order`.
- Permissions are exact: Admin may move any task; a Co-Admin may move only a task in their committee; a primary/assist assignee may change only their assigned task's status and the server places it at the destination lane's tail; assignees cannot reorder; non-assigned Members cannot move. Assignees may move backward, including Completed → In Progress. A non-Completed dependency rejects only a forward move; it never auto-reverts existing progress.
- The definer function is required because one move may rebalance neighboring rows the caller cannot directly update. Give it a dedicated `NOLOGIN` owner role with only the table privilege/RLS-bypass capability needed by this one function; authenticated users cannot assume that role, and no other callable function may share it. Replace the assignee-guard trigger function as `SECURITY INVOKER` so it can distinguish `current_user`: it permits the dedicated move owner to change only `status`/`sort_order` after the RPC's `auth.uid()` checks, while a direct authenticated caller remains limited to the existing status-only path and cannot forge `sort_order`. The Archived-parent guard remains independent, is never exempted, and runs for every changed task row.
- Use spaced integer ranks and deterministic transactional rebalancing. Client neighbor/index ids are hints only: verify they belong to the same event/phase/destination status and are current. Serialize conflicting lane moves with row/advisory locks and return a retryable conflict when safe ordering cannot be established.
- Avoid activity-log spam: pure `sort_order` changes create no activity entry; a combined status/order move creates one meaningful status-change entry attributed to `auth.uid()` and omits rank-only noise. Rebalancing neighbors produces no business activity entries.
- **Database impact:** updates only `tasks.status` and `tasks.sort_order`; adjusts the assignee/activity triggers narrowly to support the controlled RPC. New migration: **yes**. Raw `tasks_update` stays committee-scoped and is not broadened.
- **Guards that must remain true:** Archived tasks reject moves even through the definer; `event_id`, phase, dependency, assignees, and content cannot change; moves do not insert/delete tasks and cannot violate the Active-event count invariant.
- **Security risks:** a definer RPC, RLS-bypass owner, or trigger exemption can become a general bypass. Restrict callable signature, executable roles, owner-role membership, writable columns, and row counts; assert that the dedicated role owns only the intended callable function; re-read all ids; test direct-table forgery and other definer functions. Concurrency must not duplicate/drop ranks.
- **Test deliverable:** `docs/PHASE-4-STEP-5B-TESTS.md` follows the test-document contract and covers every role, forward/backward dependency behavior, tail placement for assignees, Admin/own-Co-Admin reorder, other-Co-Admin denial, dedicated-role ownership/membership, direct sort-order forgery, Archived denial, activity-log noise, and concurrent/stale moves.
- **Acceptance:** the permission matrix is enforced by the RPC and direct SQL; allowed moves persist deterministic order; assignees can move backward but never reorder; dependency locks only forward movement; Archived writes fail; pure reorder/rebalance produces no activity spam and a status move produces one attributable entry.

Check exact affected counts, fixed `search_path`, executor ownership/membership, and narrow grants; forbid a general JSON patch endpoint.

## Known limitations

- Raw `tasks` rows are not field-masked. Confidential safety depends on callers using the board/detail/access RPCs for content; raw `tasks_select` intentionally remains narrower and is not the board API.
- Only one direct dependency is supported. Multiple prerequisites and dependency graphs beyond that single pointer are out of scope.
- Blocked state and effective priority are derived, not stored. Existing dependents are not auto-reverted if a prerequisite moves backward.
- Comment edit history is not versioned; only the current body and `edited_at` are retained.
- Phase 4 stores mention/Heads Up/assignment/unlock intent but sends no notifications. Notification delivery and unread behavior are Phase 5.
- Task boards and Workspace use focus refetch/short polling. Supabase Realtime for tasks is not part of Phase 4.
- `tasks.created_by` is provenance only, and historical values are an event-creator fallback rather than proof of the original human task author.
- Optional work links, assistance polish, comments, archive late-sharing, and My Tasks are not required to pass the minimum Phase 4 gate unless the owner promotes them before implementation.
