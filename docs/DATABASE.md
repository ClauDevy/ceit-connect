# CEIT Connect — Database reference

Postgres on Supabase. **Every table has Row-Level Security (RLS) enabled** — the database, not the app, decides who can see or change each row. If anything here disagrees with `supabase/migrations/`, the migration files win (see "Verify" notes).

## Tables

### committees

`id uuid pk`, `name text`. 12 rows (President, CIA, COEXA, COMRECS, COFBUM, CARA, COPI, COPR, COBAP, COSEA, COSCA, COSRAW). A lookup table, not an enum. Any logged-in user can read; only Admin writes.

### users (app profile; one row per person)

`id uuid pk` (**must equal an `auth.users.id`** — Supabase's own login table), `email text`, `full_name text`, `role text` (`Admin` | `Co-Admin` | `Member`), `committee_id uuid → committees.id` (null for Admins), `is_active bool`, `created_at timestamptz`, `password_set bool not null default false`, `discord_id text null`, `avatar_url text null`.

- `password_set` = the person has set a password for email/password sign-in. It drives the Settings navigation reminder only and is never an authorization or Google-admission gate.
- A person always needs **both** an `auth.users` row and a `users` row. The Invite flow creates both together and rolls back the login account if the profile insert fails.
- Users are never deleted. Deactivate with `is_active = false`.
- `anonymized_at timestamptz null` is the terminal former-member marker. A
  marked row stays inactive with its UUID, role, committee, and history
  references preserved; its display identity is fixed to `Former member` and
  `<uuid>@former.invalid`, and it can never be reactivated.

### events

`id uuid pk default gen_random_uuid()`, `name text not null`, `description text`, `banner_url text`, `start_date date not null`, `end_date date`, `status text not null default 'Draft'` (`Draft` | `Active` | `Archived`), `created_by uuid not null → users.id`, `created_at timestamptz default now()`, `updated_at timestamptz not null default clock_timestamp()`.

### tasks

`id uuid pk`, `event_id uuid not null → events.id on delete cascade`, `committee_id uuid not null → committees.id`, `title text not null`, `description text`, `phase text`, `status` (`To Do` | `In Progress` | `Completed`, default `To Do`), `priority` (`Low` | `Medium` | `High` | `Critical`, default `Medium`), `task_type` (`Deliverable` | `LiveOperation`, default `Deliverable`), `due_date timestamptz`, `call_time timestamptz`, `end_time timestamptz`, `primary_assignees uuid[] default '{}'`, `assist_assignees uuid[] default '{}'`, `is_confidential bool default false`, `request_backup bool default false`, `depends_on_task_id uuid → tasks.id` (self-reference), `allowed_viewers uuid[] default '{}'`, `created_by uuid not null → users.id`, `sort_order bigint not null`, `created_at`.

- Assignee arrays hold user ids; they are **not** foreign keys. Assignees may be active users from any committee because tasks are collaborative. Membership test in policies: `auth.uid() = any(primary_assignees)`.
- `created_by` is immutable provenance only and never grants access. Historical rows use the event creator as a fallback; new authenticated inserts always derive it from `auth.uid()`.
- `sort_order` is a positive, spaced server-owned rank unique within `(event_id, phase, status)`, treating null phases as the same lane. New tasks and raw status/phase changes append at the true destination tail. Direct same-lane rank writes remain blocked; `move_task()` is the only narrow writer that may persist a deliberate rank or rebalance a lane.
- Dependencies must remain within one event, cannot point to the task itself, and cannot form a cycle. Blocked state remains derived and dependency changes never change status.

### task_work_links

`id uuid pk`, `task_id uuid not null → tasks.id on delete cascade`, nullable display `name text`, canonical `url text not null`, nullable `created_by uuid → users.id on delete set null`, and `created_at timestamptz not null default now()`.

- Names are trimmed and limited to 120 characters. URLs are trimmed, limited to 512 characters, and must be one of the canonical HTTPS Drive/Docs file, folder, document, spreadsheet, or presentation forms emitted by the app parser. A task cannot store the same canonical URL twice and is capped at 20 links.
- Creator identity is always derived from `auth.uid()`. Users are normally deactivated rather than deleted; the nullable FK preserves historical links if a profile is exceptionally removed.
- RLS is enabled with no direct authenticated table policies or privileges. Restricted reader/add/remove functions are the only client paths, and every access decision delegates to `task_content_access()`.

### task_volunteers

`task_id uuid not null → tasks.id on delete cascade`, `user_id uuid not null → users.id on delete cascade`, `created_at timestamptz not null default clock_timestamp()`, primary key `(task_id, user_id)`.

- The composite primary key is the one-offer-per-user-per-task unique constraint. `task_volunteers_user_created_idx (user_id, created_at desc, task_id)` supports a user's pending-offer lookup; partial `tasks_help_wanted_active_idx (event_id, due_date, id) where request_backup and status <> 'Completed'` supports the Help Wanted feed.
- Rows are pending offers only. RLS is enabled (not forced), table grants are revoked from `PUBLIC`, `anon`, and `authenticated`, and no permissive policies exist; fixed-shape readers and narrow mutators are the only client paths.
- `task_id` and every other column are immutable because volunteer offers have no update path. A fail-closed guard locks the stored task before its parent event, rejects every update, rejects inserts outside Active events, and freezes all child writes beneath Archived parents. Task/user removal cascades delete pending offers; users are still never deleted in normal product behavior.
- Readers surface offers only while the task still requests backup and filter out inactive users plus users already stored as primary/assist assignees. Cancelling backup deletes all offers. Every acceptance locks the task's child rows and transactionally sweeps all stale inactive/already-assigned offers. Step 8A deliberately does not rewrite the Step 7A assignment functions or the event editor merely to clean optional pending offers.

### task_comments

`id uuid pk default gen_random_uuid()`, `task_id uuid not null → tasks.id on delete cascade`, `created_by uuid not null → users.id`, `body text not null`, `is_heads_up boolean not null default false`, `mentioned_user_ids uuid[] not null default '{}'`, `created_at timestamptz not null default clock_timestamp()`, and nullable `edited_at timestamptz`.

### archived_task_viewers

`task_id uuid not null → tasks.id on delete cascade`, `user_id uuid not null → users.id on delete cascade`, `granted_by uuid not null → users.id`, and `created_at timestamptz not null default clock_timestamp()`, with primary key `(task_id, user_id)`. The table is deny-by-default: RLS is enabled, authenticated clients have no table privileges, and there are no permissive policies. Rows may exist only for Archived parents, every update is rejected, and the insert guard derives `granted_by` from `auth.uid()`.

- Bodies use a leading/trailing POSIX whitespace-class trim and must contain 1–4,000 characters afterward. A comment stores at most 20 unique, non-null mention ids. Mention arrays are normalized into UUID order, so edit no-op comparison treats mentions as an unordered set. Every role may mention any user who is active and has current `real` task-content access; the caller's raw `users` row-visibility scope does not further restrict valid targets.
- `task_comments_task_thread_idx (task_id, created_at desc, id desc)` supports stable newest-first keyset pages; `task_comments_mentions_idx` is a GIN index for future mention processing. Phase 4 creates no notification rows and changes no unread counts.
- RLS is enabled with no direct authenticated policies or table privileges. Fixed-shape readers and narrow add/edit/delete RPCs are the only client paths. Authors alone edit; authors delete their own comments; an active Admin may delete any currently accessible comment; Co-Admins have no blanket edit/delete right.
- Every read and write re-checks `task_content_access(task_id) = 'real'`. Readers raise the same `CCC01` for hidden, masked, unknown, inactive, and profile-less cases, so zero rows means only an authorized empty thread. Archived comments remain readable to current real-content viewers but are immutable.

### notifications

`id uuid pk default gen_random_uuid()`, `user_id uuid not null → users.id on delete cascade`, `type text not null` (`mention` | `assignment` | `status_change` | `unlock` | `backup_request` | `heads_up`), `task_id uuid → tasks.id on delete cascade` (nullable), `read_at timestamptz` (nullable), `created_at timestamptz not null default now()`. Private to each user (even Admins can't read others'); system-generated only; a user may mark their own as read; nobody deletes.

### activity_log

`id uuid pk default gen_random_uuid()`, `task_id uuid → tasks.id on delete set null`, `user_id uuid → users.id on delete set null`, `action text not null` (`INSERT` | `UPDATE` | `DELETE`), `changes jsonb`, `created_at timestamptz not null default now()`. Written automatically by the task trigger; no client role has direct table privileges. `list_activity_log()` is the only client read path: active Admins/Co-Admins receive the whole sequence with unavailable content reduced to a fixed minimal masked row, while current primary/assist Members may request only an exact real-access task. The fixed response excludes raw `changes` and uses `(created_at, id)` keyset paging. Batch 12b keeps every row for the same fixed 30-day window, then `purge_activity_log()` lets only a `postgres` session delete at most 5,000 oldest eligible rows through the transaction-local delete guard. Purging is irreversible: old task History disappears, including the record of who deleted a task after its DELETE row ages out. Changing the window requires one new migration replacing `activity_log_retention_days()` and the shared TypeScript constant in the same change.

Policy names for events: `events_select`, `events_insert`, `events_update`, `events_delete`.

`events_select` exposes Drafts to any active Admin or Co-Admin; `my_role()` returns `null` for inactive profiles, so Members and deactivated privileged users cannot see them. `events_update` permits any active Admin or Co-Admin to edit any Draft or Active event, including launching an eligible Draft, but its `WITH CHECK` no longer permits a raw update to produce `Archived`. Only the restricted `archive_event()` function may archive: it authorizes an active Admin before event lookup, exclusively locks the event, checks the exact `updated_at` and incomplete-task count the Admin confirmed, and then performs Active-to-Archived atomically. An Active event cannot return to Draft, a Draft cannot be archived, and an Archived event cannot be updated, un-archived, or deleted. The lifecycle trigger enforces these rules even for service-role writes; `events_delete` also excludes Archived rows as defense in depth.

Task Draft visibility is enforced separately from event visibility. `tasks_select`, both sides of `tasks_update`, and `tasks_delete` require an active profile at the top level. Active Admins have full raw access; active Co-Admins may access their own committee's tasks, including Drafts; and active primary/assist assignees may access non-Draft tasks. No backup request, allowed-viewer entry, or late-share state grants raw task visibility. In addition, every active user may read non-confidential tasks whose parent event is Archived. That branch checks the real parent status through the restricted `event_is_archived()` security-definer helper, so caller-scoped event RLS cannot hide or alter the answer; confidential Archived tasks remain limited to active Admins, active owning Co-Admins, and active assignees. A fail-closed security-definer trigger rejects every task insert, update, or delete when either its old or new parent event is Archived, regardless of caller role or RLS bypass. Activity snapshots are no longer exposed through table RLS: the fixed-shape reader applies current content access, masks Draft/confidential/deleted cases fail-closed, and searches only the final safe projection. The `get_task()` security-definer function also checks the parent status explicitly and returns no row for a Draft task unless the caller is an active Admin or the active Co-Admin of that task's committee.

## Functions and triggers

### Phase 4B Batch 0 users authorization

- After Batch 8 is applied, the effective `users` policies are `users_select_own_row`, `co_admin_view_own_committee_members`, and SELECT-only `admin_view_all_users`. Batch 8 drops `admin_full_access_users`; the former `co_admin_update_own_committee_members` policy was already dropped by Batch 0.
- `PUBLIC`, `anon`, and `authenticated` have no direct `INSERT`, `UPDATE`, or `DELETE` privilege on `public.users`. Batch 8 also adds the fail-closed `users_guard_officer_writes` trigger: profile deletion is always rejected, and officer insert/role/committee/active-state changes require a postgres-owned narrow writer plus its exact transaction-local writer token. Member-only server paths remain available.
- `update_own_profile(p_full_name text) returns text` is the only own-profile writer. It is postgres-owned, fixed-empty-path, `VOLATILE SECURITY DEFINER`, and executable only by `authenticated`. It authorizes an active profile before validating input, derives the target from `auth.uid()`, and explicitly updates only `full_name`.

### Phase 4B Batch 9 Co-Admin Member management

- `list_managed_users(p_is_active, p_search, p_offset)` is the fixed-shape User Management reader. Active Admins retain all-role/all-committee scope; active Co-Admins receive only Members in their current non-null committee. It returns exactly `id`, `full_name`, `email`, `role`, `committee_id`, `avatar_url`, and `is_active`, uses literal case-insensitive substring search across name/email/role/committee, and keeps fetch-21/show-20 ordering by `full_name, id`. The older same-committee SELECT policy remains for other features, not this management projection.
- `finalize_member_invite(p_auth_user_id, p_email, p_full_name, p_committee_id)` accepts only an unconfirmed, invited, never-signed-in matching Auth identity with no profile or live officer invitation. Admins supply a validated real committee; Co-Admins supply no committee authority and the function derives their own committee. It inserts only an active `Member` profile.
- `deactivate_committee_member(p_user_id)`, `reactivate_committee_member(p_user_id)`, and `update_committee_member_full_name(p_user_id, p_full_name)` are authenticated-only, fixed-empty-path definers for active Co-Admins targeting same-committee Members. They share the officer advisory lock/re-check pattern and write only `is_active` or normalized `full_name`; no direct authenticated `users` UPDATE policy is restored.
- Co-Admin deactivation intentionally leaves the profile avatar, Storage object, and Auth ban state unchanged in Batch 9. Batch 14 owns the avatar and ordinary-Member Auth ban/unban decision; Admin deactivation keeps its existing avatar cleanup behavior.
- Names reject raw input over 1,000 code points before the per-character scan; reject U+0000–U+001F, U+007F–U+009F, U+2028, and U+2029; trim only U+0020, U+00A0, U+1680, U+2000–U+200A, U+202F, U+205F, U+3000, and U+FEFF at the edges; and contain 1–100 Unicode code points afterward. `CCP01` means the caller profile is unavailable and `CCP02` means the name is invalid.

### Phase 4B Batch 10 former-member removal

- `preview_former_member_removal(uuid[])` and
  `anonymize_former_member(uuid)` are caller-session Admin boundaries. They
  preserve the UUID and history, refuse active/Admin/self/open-task targets,
  and return the terminal state idempotently.
- `cleanup_former_member_auth(uuid)` is a Phase 1b service-role-only,
  postgres-owned, fixed-empty-path `SECURITY DEFINER` boundary applied to Dev
  and Prod (owner-confirmed). It accepts only an inactive
  profile with non-null `anonymized_at`
  after the Admin API has proved the deterministic confirmed email and future
  ban. It deletes non-email identities; canonicalizes zero or one email
  identity without creating one; clears Auth metadata, phone/change state,
  sessions, refresh tokens, and available MFA/one-time-token/flow-state rows;
  and preserves Auth UUID, email, confirmed timestamp, password hash, ban, and
  operational timestamps. More than one email identity or a provider-ID
  collision rolls the statement back. `auth.audit_log_entries` is intentionally
  retained as a known Auth audit leftover.

### Phase 4 Step 7 controls

- `get_task_edit_controls(p_task_id uuid)` is a stable, fixed-empty-path `SECURITY DEFINER` reader for callers with `real` task access. It returns dependency/confidentiality controls to the same Step 7 roles, assignment/delete controls to active Admins and Co-Admins, and self-unassign controls to an assigned active caller. Masked/hidden callers and Archived tasks receive zero rows. It also returns current assignees plus active assignment candidates, a stable Completed/due-cutoff block code, and whether self-unassign would remove the caller's confidential access.
- `set_task_dependency(p_task_id, p_depends_on_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` content access to the dependent task, permits a `real` or safely `masked` prerequisite, intentionally supports cross-committee management, locks the stored event before the shared advisory key and task row, rechecks same-event/no-self/no-cycle rules, and writes only `depends_on_task_id`. The existing dependency trigger revalidates the write under the same lock, and status never changes.
- `set_task_confidentiality(p_task_id, p_is_confidential, p_allowed_viewers)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` public wrapper for active Admins and the owning Co-Admin. It re-establishes the former invoker authorization, real-access, and Draft/Active-parent boundary before delegating to the ungranted Step 12 implementation. It writes only confidentiality/viewers, requires a non-confidential task to have an empty list, caps viewers at 50 without nulls/duplicates, validates newly added viewers across committees through `list_active_task_assignees()`, and permits already-stored inactive viewers to remain.
- `task_dependency_allows_forward_move(p_event_id, p_depends_on_task_id)` is a minimal trigger-context-only `VOLATILE SECURITY DEFINER` boolean helper. The invoker lane trigger calls it after taking the shared event advisory lock so raw forward status updates can see an RLS-hidden prerequisite. Direct calls fail before reading; no task content is returned. `move_task()` retains its identical forward-only rule and exits through the postgres trigger branch before this raw-path helper is reached.
- `assign_task_people(p_task_id, p_primary_assignees, p_assist_assignees)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` task access, validates nulls, duplicates, overlap, the 100-person combined cap, new-active users, and retained inactive assignees, and rejects no-op requests with `CCN01`. It locks event row, event advisory key, then task row. Removing the final primary resets an In Progress task to the `To Do` tail; an already-`To Do` or Completed task keeps its status and rank.
- `delete_task(p_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` access, locks the event/advisory/task path, permits only stored `To Do` tasks, preserves the Step 5a referenced-prerequisite guard, and relies on the deferred Active-event-must-have-a-task constraint for the final invariant.
- `unassign_self(p_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It removes only `auth.uid()` from both assignment arrays. Completed tasks fail with `CCU73`; non-null due times at or before the single 72-hour cutoff fail with `CCU72`. A final-primary departure uses the shared reset helper only from In Progress; an already-`To Do` task keeps its rank, and the task activity trigger records the actor/time once.
- `prepare_unassigned_task_reset(p_event_id, p_task_id, p_phase)` is the fixed-empty-path `SECURITY INVOKER` helper used only by `assign_task_people()` and `unassign_self()`. It is ungranted to `PUBLIC`, `anon`, and `authenticated`; it computes the safe `To Do` tail and uses the same deferred-constraint rebalance pattern as `move_task()` when ranks are exhausted.
- Batch 11 supersedes the Step 8A current-state pin after its migrations are applied. The exact full update/delete writer inventory is 13 functions: `accept_task_volunteer`, `assign_task_people`, `claim_task`, `delete_task`, `edit_active_event_task`, `edit_event_with_tasks`, `guard_event_updates`, `move_task`, `prepare_unassigned_task_reset`, `set_task_backup_request`, `set_task_confidentiality`, `set_task_dependency`, and `unassign_self`. The exact postgres-owned, non-trigger, `SECURITY DEFINER` update/delete inventory is 10: `accept_task_volunteer`, `assign_task_people`, `claim_task`, `delete_task`, `edit_active_event_task`, `edit_event_with_tasks`, `move_task`, `set_task_backup_request`, `set_task_dependency`, and `unassign_self`. The exact task insert writers are `create_active_event_task`, `create_event_with_tasks`, and `edit_event_with_tasks`. Historical migration assertions remain historical; the current catalog tests own these lists.
- The exact functions that write either assignment array are eight: `accept_task_volunteer`, `assign_task_people`, `claim_task`, `create_active_event_task`, `create_event_with_tasks`, `edit_active_event_task`, `edit_event_with_tasks`, and `unassign_self`. The exact trusted assignee markers are those same names. `create_active_event_task` and `edit_active_event_task` are the only new markers.
- The ordinary privileged owner branch remains the exact six-column union `status | sort_order | depends_on_task_id | primary_assignees | assist_assignees | request_backup`. `edit_event_with_tasks` has its own exact union `title | description | committee_id | phase | priority | task_type | due_date | call_time | end_time | primary_assignees`. `edit_active_event_task` has the smallest required union `title | description | committee_id | phase | priority | task_type | due_date | call_time | end_time | primary_assignees | assist_assignees | is_confidential | allowed_viewers | status | sort_order`. Assists are included only to preserve them while removing a promoted primary; status is included only for the final-primary In Progress → To Do reset; rank is included only for database-controlled destination-tail placement after that reset or a phase change. Neither status nor rank is caller-supplied. No policy is replaced.

### Phase 4B Batch 11 task mutation boundary

- `tasks.updated_at` is a non-null database token. Existing rows receive the migration transaction timestamp from the `ADD COLUMN` default. No trigger is disabled and `session_replication_role` is never changed. Treat the value as an opaque string outside PostgreSQL; JavaScript must not parse and reserialize it through `Date`.
- `tasks_z4_set_updated_at` is alphabetically last among the real `BEFORE UPDATE` triggers and therefore runs after `tasks_z2_set_destination_lane_order`. `prepare_unassigned_task_reset` is not a trigger: it computes the final status/rank before the single row update, so z4 still observes the finished business row. The timestamp trigger advances monotonically for meaningful task-row changes, preserves the token for rank-only writes, and overwrites forged values. `log_task_activity()` removes `updated_at` from comparisons and snapshots; status-only edits remain ordinary `UPDATE` activity.
- `create_active_event_task` and `edit_active_event_task` are postgres-owned, fixed-empty-path, `VOLATILE SECURITY DEFINER` functions granted only to `authenticated`. Their exact writer markers are their function names. Both re-read an active stored profile after lock waits, derive security-owned fields, avoid dynamic SQL, and require exact affected-row counts. Editing a confidential task requires `real` content access before and after locking.
- `get_task_stored_priority(p_task_id uuid)` is a postgres-owned, fixed-empty-path `STABLE SECURITY DEFINER` scalar reader granted only to `authenticated`. It returns the stored priority only to an active Admin or active owning Co-Admin when the parent is Active and `task_content_access()` is `real`; every unauthorized, masked, Draft, Archived, missing, or otherwise unavailable case returns null without task-revealing error text. It exists separately from `get_task_detail()`, whose effective-priority presentation contract remains unchanged.
- New tasks derive `event_id`, `created_by`, `status = 'To Do'`, and the destination tail in the database and start with no assists. Edit preserves assists; promoting an existing assist to primary removes that UUID from assists. Any pending volunteer row for a resulting primary or assist is redundant and is deleted.
- Confidentiality keeps every Step 7 validation rule: required boolean/list, 50-viewer cap, no nulls/duplicates, an empty list when non-confidential, and active newly added viewers while already-stored inactive viewers may be retained. The complete differences are: these two writers are definer-security rather than the standalone invoker writer; they accept only Active parents rather than Draft or Active; confidentiality is atomic with the task content/assignment write; Add has no retained set so every viewer must be active; Edit compares against the locked stored viewer set; and authorization is the new RPC's repeated stored-profile/real-content/owning-committee boundary. The Draft/Edit Event form and standalone Step 7 writer are unchanged.
- Emptying primaries mirrors `assign_task_people`: an In Progress task resets to `To Do` and its destination tail; a Completed task stays Completed. The reset status/rank and assignment/content changes occur in the same guarded task update, so the owner guard observes the full exact union.
- A phase change appends to the true destination lane tail, including RLS-hidden rows. Edit Event uses the same rule rather than retaining the source rank.
- `enforce_event_task_capacity()` is a shared invoker-security `BEFORE INSERT` trigger that locks the event row `FOR SHARE`, then takes the event advisory lock, then calls `count_event_tasks_for_capacity(uuid)`. The count helper is a postgres-owned, fixed-empty-path, `VOLATILE SECURITY DEFINER` scalar so its post-wait snapshot sees every task regardless of caller RLS; it raises `42501` outside trigger context, is revoked from `PUBLIC`/`anon`, and is executable by `authenticated` only because the invoker trigger must call it. The limit is 200. Edit Event's temporary exception is bounded by `stored_count < starting_count + submitted_additions`, and its final check permits a legacy over-cap event only when the save does not increase the total.
- Lock paths preserve the global event-row → event-advisory → task-row order. Create Event takes sorted proposed-assignee user locks, owns the newly inserted event row, then reaches the capacity parent/advisory locks and task inserts. Edit Event retains sorted stored/proposed user locks, event `FOR UPDATE`, advisory, then its original loop-acquired task rows. Template import saves through Create Event. Add Task locks only existing proposed primaries, then event `FOR SHARE`, advisory, and insert. Edit Task locks only the existing union of discovered stored primaries/assists and proposed primaries, then event `FOR SHARE`, advisory, task `FOR UPDATE`, and recomputes the same union; mismatch alone is `CCL01`. Direct insert uses capacity event `FOR SHARE`, advisory, count, then insertion. Viewers are never user-lock inputs. The three older backup paths with task-before-event order remain a separate Batch 14 finding.
- In the one-task editor, a missing locked task is `42501` with “The task is unavailable.”; only a genuine authoritative assignment-lock-set mismatch is `CCL01`; stale expected `updated_at` and zero-row optimistic updates are `CCS01` with “This task changed after you loaded it. Reload and try again.” Edit Event has no per-task token and retains its original `40001` zero-row task-update behavior.
- Batch 13b must add both new RPC names to its completed-phase mutation guard. The phase trigger can then reject their insert/update before the row changes, while the existing approved reopen writer remains the only way to mutate a completed phase.

- `task_volunteers_guard_writes` trigger — uses the child-specific task-row then event-row order, revalidates stored parentage, rejects inserts outside Active events, freezes every child write under Archived parents with `CCB08`, and rejects every update (including `task_id`) with `CCB09`. Nested task-FK cascades are allowed only after the task's own guard has approved deletion.
- `events_set_updated_at` trigger on `events` — assigns a monotonic value based on `clock_timestamp()` before every event update. The edit RPC always updates the event row, including task-only saves, so every successful edit advances the concurrency token.
- `events_guard_banner_url` trigger on `events` — permits a null banner or a Supabase public banner URL for that event's own `<event_id>/<uuid>.webp` object, and verifies the object already exists through a fixed-search-path security-definer helper. This closes direct insert/update paths that could otherwise store arbitrary URLs.
- `events_require_task_when_inserted_active` / `tasks_preserve_active_event_task_on_delete` / `tasks_preserve_active_event_task_on_event_move` — deferred constraint triggers that enforce at transaction end that a newly inserted Active event and an Active event affected by task deletion or a real `event_id` change retain at least one task. They do not fire for ordinary event/task updates; Drafts may remain empty, same-transaction replacements work, and event deletion remains compatible.
- Known, accepted limitation: the raw `tasks` row is not field-masked at the column-grant level. A confidential raw row is available only to an active Admin, active owning Co-Admin, or active non-Draft primary/assist assignee. Restricted RPCs—not raw `SELECT`—serve allowed viewers and any future archive late-share viewers. Permanent direct-`SELECT` regression tests guard this boundary.

## Storage

Bucket `avatars`: public read, 2 MB limit, MIME types `image/jpeg`, `image/png`, `image/webp`. Files live at `<user_id>/avatar.webp` (one fixed filename, so re-uploading overwrites). Storage RLS: anyone can read; a user can insert/update/delete only inside the folder named after their own `auth.uid()`. **The bucket itself is not created by migrations** — create it by hand in each environment; the migration only creates the policies.

Bucket `banners`: public read, 2 MB limit, MIME types `image/jpeg`, `image/png`, `image/webp`; it is created by the Step 7 migration. Saved app files live at `<event_id>/<random_uuid>.webp`. Storage writes require an active Admin or Co-Admin and an existing Draft or Active event matching the first folder segment. Missing/malformed events, Members, inactive users, and Archived events fail closed. Replacements use a new filename, update `events.banner_url` first, and only then delete the former object.

Known Storage limitation: Postgres and Storage cannot share a transaction. Directly deleting a Draft event, an archive race between upload and URL save, or a Storage outage during post-update cleanup can leave an unreferenced banner object. Cleanup never bypasses the Archived-event freeze.
