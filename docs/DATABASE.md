# CEIT Connect — Database reference

Postgres on Supabase. **Every table has Row-Level Security (RLS) enabled** — the database, not the app, decides who can see or change each row. If anything here disagrees with `supabase/migrations/`, the migration files win (see "Verify" notes).

## Tables

### committees

`id uuid pk`, `name text`. 12 rows (President, CIA, COEXA, COMRECS, COFBUM, CARA, COPI, COPR, COBAP, COSEA, COSCA, COSRAW). A lookup table, not an enum. Any logged-in user can read; only Admin writes.

### users (app profile; one row per person)

`id uuid pk` (**must equal an `auth.users.id`** — Supabase's own login table), `email text`, `full_name text`, `role text` (`Admin` | `Co-Admin` | `Member`), `committee_id uuid → committees.id` (null for Admins), `is_active bool`, `created_at timestamptz`, `password_set bool not null default false`, `discord_id text null`, `avatar_url text null`.

- `password_set` = the person has completed a real first login and set a password; Google sign-in is gated on it.
- A person always needs **both** an `auth.users` row and a `users` row. The Invite flow creates both together and rolls back the login account if the profile insert fails.
- Users are never deleted. Deactivate with `is_active = false`.

### events

`id uuid pk default gen_random_uuid()`, `name text not null`, `description text`, `banner_url text`, `start_date date not null`, `end_date date`, `status text not null default 'Draft'` (`Draft` | `Active` | `Archived`), `created_by uuid not null → users.id`, `created_at timestamptz default now()`, `updated_at timestamptz not null default clock_timestamp()`.

### tasks

`id uuid pk`, `event_id uuid not null → events.id on delete cascade`, `committee_id uuid not null → committees.id`, `title text not null`, `description text`, `phase text`, `status` (`To Do` | `In Progress` | `Completed`, default `To Do`), `priority` (`Low` | `Medium` | `High` | `Critical`, default `Medium`), `task_type` (`Deliverable` | `LiveOperation`, default `Deliverable`), `due_date timestamptz`, `call_time timestamptz`, `end_time timestamptz`, `primary_assignees uuid[] default '{}'`, `assist_assignees uuid[] default '{}'`, `is_confidential bool default false`, `request_backup bool default false`, `depends_on_task_id uuid → tasks.id` (self-reference), `allowed_viewers uuid[] default '{}'`, `created_by uuid not null → users.id`, `sort_order bigint not null`, `created_at`.

- Assignee arrays hold user ids; they are **not** foreign keys. Assignees may be active users from any committee because tasks are collaborative. Membership test in policies: `auth.uid() = any(primary_assignees)`.
- `created_by` is immutable provenance only and never grants access. Historical rows use the event creator as a fallback; new authenticated inserts always derive it from `auth.uid()`.
- `sort_order` is a positive, spaced server-owned rank unique within `(event_id, phase, status)`, treating null phases as the same lane. New tasks and raw status/phase changes append at the true destination tail. Direct same-lane rank writes remain blocked; `move_task()` is the only narrow writer that may persist a deliberate rank or rebalance a lane.
- Dependencies must remain within one event, cannot point to the task itself, and cannot form a cycle. Blocked state remains derived and dependency changes never change status.

### task_work_links

`id uuid pk`, `task_id uuid not null → tasks.id on delete cascade`, nullable display `name text`, canonical `url text not null`, nullable `created_by uuid → users.id on delete set null`, and `created_at timestamptz not null default now()`.

- Names are trimmed and limited to 120 characters. URLs are trimmed, limited to 512 characters, and must be one of the canonical HTTPS Drive/Docs file, folder, document, spreadsheet, or presentation forms emitted by the app parser. A task cannot store the same canonical URL twice and is capped at 20 links.
- Creator identity is always derived from `auth.uid()`. Users are normally deactivated rather than deleted; the nullable FK preserves historical links if a profile is exceptionally removed.
- RLS is enabled with no direct authenticated table policies or privileges. Restricted reader/add/remove functions are the only client paths, and every access decision delegates to `task_content_access()`.

### task_volunteers

`task_id uuid not null → tasks.id on delete cascade`, `user_id uuid not null → users.id on delete cascade`, `created_at timestamptz not null default clock_timestamp()`, primary key `(task_id, user_id)`.

- The composite primary key is the one-offer-per-user-per-task unique constraint. `task_volunteers_user_created_idx (user_id, created_at desc, task_id)` supports a user's pending-offer lookup; partial `tasks_help_wanted_active_idx (event_id, due_date, id) where request_backup and status <> 'Completed'` supports the Help Wanted feed.
- Rows are pending offers only. RLS is enabled (not forced), table grants are revoked from `PUBLIC`, `anon`, and `authenticated`, and no permissive policies exist; fixed-shape readers and narrow mutators are the only client paths.
- `task_id` and every other column are immutable because volunteer offers have no update path. A fail-closed guard locks the stored task before its parent event, rejects every update, rejects inserts outside Active events, and freezes all child writes beneath Archived parents. Task/user removal cascades delete pending offers; users are still never deleted in normal product behavior.
- Readers surface offers only while the task still requests backup and filter out inactive users plus users already stored as primary/assist assignees. Cancelling backup deletes all offers. Every acceptance locks the task's child rows and transactionally sweeps all stale inactive/already-assigned offers. Step 8A deliberately does not rewrite the Step 7A assignment functions or the event editor merely to clean optional pending offers.

### notifications

`id uuid pk default gen_random_uuid()`, `user_id uuid not null → users.id on delete cascade`, `type text not null` (`mention` | `assignment` | `status_change` | `unlock` | `backup_request` | `heads_up`), `task_id uuid → tasks.id on delete cascade` (nullable), `read_at timestamptz` (nullable), `created_at timestamptz not null default now()`. Private to each user (even Admins can't read others'); system-generated only; a user may mark their own as read; nobody deletes.

### activity_log

`id uuid pk default gen_random_uuid()`, `task_id uuid → tasks.id on delete set null`, `user_id uuid → users.id on delete set null`, `action text not null` (`INSERT` | `UPDATE` | `DELETE`), `changes jsonb`, `created_at timestamptz not null default now()`. Written automatically by a trigger on every task INSERT/UPDATE/DELETE; nobody writes it by hand and nothing is ever edited or deleted. Admins see all rows; everyone else sees entries only for tasks they would genuinely have access to (narrower than "can see the task exists" — it was tightened twice to stop confidential and backup-flagged tasks leaking).

Policy names for events: `events_select`, `events_insert`, `events_update`, `events_delete`.

`events_select` exposes Drafts to any active Admin or Co-Admin; `my_role()` returns `null` for inactive profiles, so Members and deactivated privileged users cannot see them. `events_update` permits any active Admin or Co-Admin to edit any Draft or Active event, including launching an eligible Draft, but its `WITH CHECK` no longer permits a raw update to produce `Archived`. Only the restricted `archive_event()` function may archive: it authorizes an active Admin before event lookup, exclusively locks the event, checks the exact `updated_at` and incomplete-task count the Admin confirmed, and then performs Active-to-Archived atomically. An Active event cannot return to Draft, a Draft cannot be archived, and an Archived event cannot be updated, un-archived, or deleted. The lifecycle trigger enforces these rules even for service-role writes; `events_delete` also excludes Archived rows as defense in depth.

Task Draft visibility is enforced separately from event visibility. `tasks_select`, both sides of `tasks_update`, and `tasks_delete` require an active profile at the top level. Active Admins have full raw access; active Co-Admins may access their own committee's tasks, including Drafts; and active primary/assist assignees may access non-Draft tasks. No backup request, allowed-viewer entry, or late-share state grants raw task visibility. In addition, every active user may read non-confidential tasks whose parent event is Archived. That branch checks the real parent status through the restricted `event_is_archived()` security-definer helper, so caller-scoped event RLS cannot hide or alter the answer; confidential Archived tasks remain limited to active Admins, active owning Co-Admins, and active assignees. A fail-closed security-definer trigger rejects every task insert, update, or delete when either its old or new parent event is Archived, regardless of caller role or RLS bypass. `activity_log_select` repeats the Draft parent-status and content checks because `changes` stores full task snapshots; its `tasks` subquery runs under the hardened `tasks_select`, keeping inactive and profile-less callers closed out, and every future `tasks_select` change must keep Step 1A TEST 9 passing. The `get_task()` security-definer function also checks the parent status explicitly and returns no row for a Draft task unless the caller is an active Admin or the active Co-Admin of that task's committee.

## Functions and triggers

### Phase 4 Step 7 controls

- `get_task_edit_controls(p_task_id uuid)` is a stable, fixed-empty-path `SECURITY DEFINER` reader for callers with `real` task access. It returns dependency/confidentiality controls to the same Step 7 roles, assignment/delete controls to active Admins and Co-Admins, and self-unassign controls to an assigned active caller. Masked/hidden callers and Archived tasks receive zero rows. It also returns current assignees plus active assignment candidates, a stable Completed/due-cutoff block code, and whether self-unassign would remove the caller's confidential access.
- `set_task_dependency(p_task_id, p_depends_on_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` content access to the dependent task, permits a `real` or safely `masked` prerequisite, intentionally supports cross-committee management, locks the stored event before the shared advisory key and task row, rechecks same-event/no-self/no-cycle rules, and writes only `depends_on_task_id`. The existing dependency trigger revalidates the write under the same lock, and status never changes.
- `set_task_confidentiality(p_task_id, p_is_confidential, p_allowed_viewers)` is a fixed-empty-path `VOLATILE SECURITY INVOKER` writer for active Admins and the owning Co-Admin. Existing task/event RLS remains active. It writes only confidentiality/viewers, rejects Archived or unavailable parents, requires a non-confidential task to have an empty list, caps viewers at 50 without nulls/duplicates, validates newly added viewers across committees through `list_active_task_assignees()`, and permits already-stored inactive viewers to remain.
- `task_dependency_allows_forward_move(p_event_id, p_depends_on_task_id)` is a minimal trigger-context-only `VOLATILE SECURITY DEFINER` boolean helper. The invoker lane trigger calls it after taking the shared event advisory lock so raw forward status updates can see an RLS-hidden prerequisite. Direct calls fail before reading; no task content is returned. `move_task()` retains its identical forward-only rule and exits through the postgres trigger branch before this raw-path helper is reached.
- `assign_task_people(p_task_id, p_primary_assignees, p_assist_assignees)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` task access, validates nulls, duplicates, overlap, the 100-person combined cap, new-active users, and retained inactive assignees, and rejects no-op requests with `CCN01`. It locks event row, event advisory key, then task row. Removing the final primary resets an In Progress task to the `To Do` tail; an already-`To Do` or Completed task keeps its status and rank.
- `delete_task(p_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It requires an active Admin/Co-Admin with `real` access, locks the event/advisory/task path, permits only stored `To Do` tasks, preserves the Step 5a referenced-prerequisite guard, and relies on the deferred Active-event-must-have-a-task constraint for the final invariant.
- `unassign_self(p_task_id)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. It removes only `auth.uid()` from both assignment arrays. Completed tasks fail with `CCU73`; non-null due times at or before the single 72-hour cutoff fail with `CCU72`. A final-primary departure uses the shared reset helper only from In Progress; an already-`To Do` task keeps its rank, and the task activity trigger records the actor/time once.
- `prepare_unassigned_task_reset(p_event_id, p_task_id, p_phase)` is the fixed-empty-path `SECURITY INVOKER` helper used only by `assign_task_people()` and `unassign_self()`. It is ungranted to `PUBLIC`, `anon`, and `authenticated`; it computes the safe `To Do` tail and uses the same deferred-constraint rebalance pattern as `move_task()` when ranks are exhausted.
- Step 8A supersedes the Step 7A current-state pin: the assignee guard's postgres-owner branch permits exactly `status`, `sort_order`, `depends_on_task_id`, `primary_assignees`, `assist_assignees`, and `request_backup`. The exact non-trigger postgres-owned `SECURITY DEFINER` functions whose own bodies directly update/delete `public.tasks` are `accept_task_volunteer`, `assign_task_people`, `claim_task`, `delete_task`, `move_task`, `set_task_backup_request`, `set_task_dependency`, and `unassign_self`. The broader 12-function direct-writer set additionally contains `edit_event_with_tasks`, `guard_event_updates`, `prepare_unassigned_task_reset`, and `set_task_confidentiality`. Historical migrations retain the smaller inventory assertions that were true when each migration ran; Step 8 TEST 1 is the authoritative current-catalog assertion.

### Phase 4 Step 8A controls

- `claim_task(p_task_id uuid)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer executable only by `authenticated`. Any active role may claim a real-content, non-Completed Active-event task with zero primary assignees. A caller already in `assist_assignees` is rejected with `CCB04`; masked confidential shells can never be claimed. Immediately after the event re-check it verifies real access before revealing lifecycle or completion errors. It locks task then event and writes only `primary_assignees`, so status, rank, and an unmet dependency remain unchanged.
- `set_task_backup_request(p_task_id uuid, p_request_backup boolean)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer for an active Admin, active Co-Admin, or current primary assignee with real content access. Real access and role/primary authority are checked immediately after the event re-check, before lifecycle/completion errors. It accepts only incomplete Active-event tasks, writes only `request_backup`, rejects no-ops with `CCB05`, and deletes every pending offer when cancelling.
- `volunteer_for_task(p_task_id uuid)` and `withdraw_task_volunteer(p_task_id uuid)` are fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` child writers for active callers. Volunteering checks real access immediately after the event re-check before lifecycle/completion errors, then requires an incomplete Active-event task currently requesting backup and rejects current primary/assist assignees. Withdrawal derives the volunteer from `auth.uid()` and deletes only that caller's pending row.
- `accept_task_volunteer(p_task_id uuid, p_user_id uuid)` is a fixed-empty-path, postgres-owned `VOLATILE SECURITY DEFINER` writer for an active Admin, active Co-Admin, or current primary assignee with real access. Real access and role/primary authority are checked immediately after the event re-check, before lifecycle/completion errors. It locks task, event, then all task child rows in user order; every inactive/already-assigned offer is swept, while an active valid selected volunteer is appended once to `assist_assignees` and produces exactly one existing task-activity row. A valid acceptance is rejected with `CCB10` when the stored primary-plus-assist count is already the same 100-person combined cap enforced by `assign_task_people()`. Selecting a stale offer returns a non-accepted outcome with no task activity. Acceptance leaves `request_backup` true until an authorized caller cancels it.
- `get_task_backup_state(p_task_id uuid)` is a fixed-shape `STABLE SECURITY DEFINER` reader for active real-content viewers of an Active task. It returns server-computed capabilities and own-offer state; full volunteer identities are returned only to callers currently allowed to accept. Inactive and already-assigned offers are filtered.
- `list_help_wanted_tasks(p_limit integer, p_offset integer)` is a fixed-shape `STABLE SECURITY DEFINER` reader for active callers. It returns only incomplete backup-requested tasks in Active events for which the caller has `real` content access. Confidential masked shells are omitted completely, so backup state cannot recreate the earlier confidential activity-log leak.
- `list_active_task_assignees_with_workload()` is a separate fixed-shape `STABLE SECURITY DEFINER` leadership reader. It preserves `list_active_task_assignees()` unchanged and returns the same active-user profile fields plus a distinct count of `To Do`/`In Progress` assignments under Active events only; Draft, Archived, and Completed tasks do not count.
- Step 8A task/child mutators use task-row then stored-event-row locking. They do not take the event advisory key because none reads or changes dependency graphs or lane ranks; the task lock is the common serialization point for claim/backup/offer races. SQLSTATEs are `CCB01` unavailable task, `CCB02` non-Active lifecycle, `CCB03` no longer claimable, `CCB04` claimant already assists, `CCB05` backup-state conflict, `CCB06` offer conflict, `CCB07` volunteer already assigned, `CCB08` Archived-child freeze, `CCB09` immutable volunteer update, and `CCB10` combined 100-assignee cap reached.

### Phase 4 Step 9A personal feed

- `list_my_tasks(p_status text default null, p_sort text default 'deadline', p_limit integer default 50, p_offset integer default 0)` is a fixed-empty-path, postgres-owned `STABLE SECURITY DEFINER` reader executable only by `authenticated`. It derives the caller from `auth.uid()` and returns `out_id`, `out_title`, `out_event_id`, `out_event_name`, `out_phase`, `out_status`, `out_effective_priority`, `out_due_date`, `out_committee_id`, `out_committee_name`, `out_is_primary`, `out_is_assist`, and `out_request_backup`. It includes only the caller's primary or assist assignments from Active events; assigned confidential tasks return real content, Draft and Archived events are excluded, and Completed tasks are included but ordered after every open task before the selected Deadline/Priority/Event ordering. `p_status` accepts null, `To Do`, `In Progress`, or `Completed`; paging is capped at 100 rows. SQLSTATEs are `CCF01` inactive or profile-less caller, `CCF02` invalid/null paging, `CCF03` invalid status, and `CCF04` invalid/null sort.

- `my_role()` and `my_committee_id()` — `SECURITY DEFINER` helpers that read the caller's role/committee without re-triggering `users` RLS. They exist to avoid the **infinite-recursion** bug (a `users` policy that queries `users`). Reuse them in new policies instead of subquerying `users`.
- `get_task(p_task_id uuid)` — `SECURITY DEFINER` with a fixed empty `search_path`, returns the real row or a masked "Confidential Task" row (see `ARCHITECTURE.md` §6). It now uses the shared lifecycle-aware content helper: inactive and profile-less callers receive zero rows, and Draft tasks return no row unless the caller is an active Admin or the active Co-Admin of the task's committee.
- `task_content_access(p_task_id uuid)` — restricted, fixed-empty-`search_path` `SECURITY DEFINER` helper shared by `get_task()` and the board RPC. It returns only `real`, `masked`, or `hidden`; `public`, `anon`, and `authenticated` cannot execute it directly.
- `calculate_effective_task_priority(p_priority text, p_due_date timestamptz, p_as_of timestamptz, p_status text)` — internal-only fixed-empty-`search_path` helper used by the board RPC. Completed tasks retain their stored priority; other tasks become Critical when overdue or High when a stored Low/Medium priority is due within 24 hours. Its accepted stored priority values are `Low`, `Medium`, `High`, and `Critical`, and `public`, `anon`, and `authenticated` cannot execute it directly.
- `list_event_board_tasks(p_event_id uuid, p_committee_id uuid)` — stable, fixed-shape `SECURITY DEFINER` board reader for active profiles. It preserves the existing 12-column shape, masking, grants, and lifecycle rules. `is_backlog` means no primary assignees and a non-Completed status, regardless of assist assignees. Rows use the server-owned lane order (`sort_order`, then `id`) without exposing `sort_order` in the return shape, so moves and same-lane Undo survive refetch. It is capped by the existing 200-task event limit.
- `get_task_detail(p_task_id uuid)` — stable, fixed-shape, fixed-empty-`search_path` `SECURITY DEFINER` reader for active profiles. It uses `task_content_access()` as its only real/masked/hidden decision, returns full safe detail for real viewers, only id/title/phase/status for a masked shell, and zero rows when hidden. Real rows include board-matching effective priority, safe assignee profiles, a confidentiality-aware dependency label without the dependency id, and active additional viewers from `allowed_viewers`; only `authenticated` may execute it.
- `get_task_work_links(p_task_id uuid)` — stable, fixed-empty-`search_path` `SECURITY DEFINER` reader. A real viewer receives exactly one row containing server-computed `can_add` and an ordered JSON link list with per-link boolean `can_remove`, which is false rather than null when a deleted creator leaves `created_by` null, including an empty list when nothing is saved. Masked/hidden callers receive zero rows. Archived links remain readable with every write flag false.
- `add_task_work_link(p_task_id, p_name, p_url)` / `remove_task_work_link(p_link_id)` — fixed-empty-`search_path` `SECURITY DEFINER` mutators executable only by `authenticated`. Add accepts only the app parser's canonical URL output, derives the creator, and is limited to active primary/assist assignees with real access. Remove permits the creator or an active Admin/Co-Admin only while that caller still has real access. Neither path writes tasks or events.
- `list_active_task_assignees()` — `SECURITY DEFINER`, fixed `search_path`, and executable only by `authenticated`. It returns `id`, `full_name`, `committee_id`, and `avatar_url` for active users only, and returns no rows unless the caller is an active Admin or Co-Admin. It exists so the collaborative assignee picker can cross committee boundaries without loosening `users` RLS or exposing email, role, or Discord data.
- `event_is_archived(p_event_id)` — restricted, fixed-empty-`search_path` `SECURITY DEFINER` boolean helper used only by the Archived branch of `tasks_select`. Its fully qualified lookup reads the real parent row independently of caller event visibility; only `authenticated` may execute it.
- `list_archived_event_assignees(p_event_id)` — fixed-empty-`search_path` `SECURITY DEFINER`, executable only by `authenticated`. It returns only `id`, `full_name`, and `avatar_url` for users present in the primary or assist arrays of that Archived event's non-confidential tasks. The caller must be active, non-Archived events return no rows, and deactivated assignees remain named without loosening `users` RLS or exposing email, role, Discord, or committee data.
- `task_update_assignees_are_valid(p_task_id, p_assignee_ids)` — restricted, fixed-`search_path` `SECURITY DEFINER` validation helper that returns only a boolean and never returns profile fields. For an authorized Admin or owning Co-Admin, it reads the task's real stored `primary_assignees`: every proposed id must still exist, newly added ids must be active, and an already-stored id may remain after that user is deactivated. It does not loosen `users` RLS or expose inactive names.
- `create_event_with_tasks(...)` — unchanged `SECURITY INVOKER`; atomically inserts one Draft/Active event and up to 200 initial tasks while RLS remains active. It derives the event creator from `auth.uid()`, rejects an Active event with zero tasks, caps text lengths, validates required JSON keys/types plus enums/dates/times, and requires every assignee to exist and be active. The task creation-metadata trigger derives each task's creator from the same authenticated caller and appends it to its initial lane. Assignees may belong to any committee, are written to `primary_assignees`, and an empty array leaves the task in the Backlog. Live Operations may save `call_time` and optional `end_time` using the existing task columns.
- `get_archived_event_template(p_template_event_id, p_new_start_date)` — read-only `SECURITY INVOKER` with a fixed empty `search_path`. It is restricted to active Admins/Co-Admins and rejects non-Archived events. Admins may import every RLS-visible committee; Co-Admins have an additional explicit own-committee predicate so assignment or `request_backup` visibility can never pull another committee's task into an import. The same scope applies to the confidential-task count. Confidential tasks are counted but excluded before title/description JSON is constructed. Every returned task has empty assignees and `To Do` status; each non-null due/call/end timestamp is shifted by the integer day difference between the new and archived event start dates. Null timestamps stay null, and more than 200 importable tasks is rejected.
- `edit_event_with_tasks(...)` — `SECURITY INVOKER`; atomically edits a Draft/Active event using an exact expected `updated_at` value plus explicit task-add, task-update, and task-delete lists. It locks and reads the stored event, then takes that event's shared task/dependency advisory lock before reading or writing task rows. All previous validation and mutation behavior remains: stale saves fail, task status/confidentiality/dependency/event fields stay protected, every requested update/delete must affect exactly one RLS-authorized row, additions require active assignees, stored inactive assignees may remain, and Co-Admins stay own-committee. A phase change appends the task to the destination lane; the RPC still never changes status. Referenced prerequisites cannot be deleted, and submitted deletions remain sequential, so a dependent must be removed before its prerequisite. Task mutations happen before Draft-to-Active and the event update remains last.
- `task_dependency_lock_key(p_event_id uuid)` — immutable, strict, empty-path pure hash helper. `authenticated` may execute it because it reveals only a deterministic bigint derived from a UUID; `PUBLIC` and `anon` cannot. Every task ordering/dependency writer uses this exact key, including the edit RPC and `set_task_dependency()`.
- `move_task(p_task_id, p_expected_phase, p_expected_status, p_destination_status, p_previous_neighbor_id, p_next_neighbor_id)` — one of the eight non-trigger `SECURITY DEFINER` functions owned by `postgres` whose own body directly updates or deletes from `public.tasks`. It has a fixed empty search path, is executable only by `authenticated`, derives and rechecks the active caller, locks the stored event before the shared event advisory key and task rows, and writes only `status`/`sort_order`. Admins may move any task; Co-Admins remain own-committee; primary/assist Members may change status on Active tasks and always land at the true destination tail but cannot reorder. It revalidates expected phase/status plus same-lane neighbor or boundary hints, gates only forward movement on an incomplete dependency, deterministically rebalances spaced ranks under the deferrable lane constraint, and returns only the moved task's id/status/rank.
- `task_lane_tail_sort_order(p_event_id, p_phase, p_status, p_exclude_task_id)` — minimal read-only `VOLATILE SECURITY DEFINER` helper used by the invoker-security destination-order trigger so a Member's raw status change sees hidden lane rows and reaches the true tail. It must stay volatile so its lane query takes a fresh snapshot after the per-event advisory lock. Only `authenticated` may execute it, and a top-level call fails with `42501` before reading; during trigger execution it returns only one scalar maximum rank and exposes no row, count, id, or task content.
- Task lock order is explicit: the edit RPC takes stored event `FOR UPDATE`, then the event advisory lock, then task rows; raw inserts take the archive guard's event `FOR SHARE`, then the advisory lock, then read the lane; raw updates necessarily start with the task row, then the archive guard's event `FOR SHARE`, then the advisory lock and graph/lane read. That raw-row inversion can deadlock against the RPC and is returned as retryable SQLSTATE `40P01`, never committed as a partial change.
- `archive_event(p_event_id, p_expected_incomplete_task_count, p_expected_updated_at)` — restricted, fixed-empty-`search_path` `SECURITY DEFINER`, executable only by `authenticated`, and returns `void`. It derives the caller from `auth.uid()` and verifies an active Admin before looking up the event, locks the event row with `FOR UPDATE`, requires current `Active` status, re-counts exactly the tasks whose status is not `Completed`, compares the count and exact microsecond-capable event version the Admin confirmed, and archives atomically. It never locks task rows or returns task content. Stable SQLSTATE codes `CCA01`–`CCA10` let the route map failures without matching message text.
- Activity-log trigger on `tasks` remains `SECURITY DEFINER` so it can write the otherwise restricted log. INSERT/DELETE and every non-rank UPDATE retain their existing snapshots and `auth.uid()` attribution; an UPDATE whose only difference is `sort_order` writes nothing, so reorders and neighbor rebalances create no business-activity noise. The attached invoker-security **assignee-guard trigger** still limits a direct plain-assignee update to status only. Its literal `current_user = 'postgres'` branch permits exactly `status`, `sort_order`, `depends_on_task_id`, `primary_assignees`, `assist_assignees`, and `request_backup`; migration/catalog assertions pin the eight non-trigger definer owner-branch writers, the separate invoker reset helper contract, and the 12-function full direct-writer inventory.
- `guard_event_updates` trigger on `events` — rejects updates where `new.created_by is distinct from old.created_by`, status changes from Active back to Draft, Draft-to-Active transitions when the event has no tasks, every non-Active-to-Archived transition, and every update or delete of an Archived event. Its `SECURITY DEFINER` function has a fixed empty `search_path`, so its task checks see every committee instead of being narrowed by the caller's task RLS. For an allowed Draft/Active event deletion, it removes child tasks while the parent remains verifiable; the existing task/activity/notification cascades still run.
- `tasks_guard_archived_event_writes` trigger on `tasks` — a fixed-empty-`search_path`, `SECURITY DEFINER`, fail-closed guard that derives parentage from stored task rows, locks every distinct old/new parent event with `FOR SHARE` in deterministic UUID order, and only then re-reads status. It rejects inserts into, updates within or moves into/out of, and deletes from Archived events. It runs before the assignee guard; rejected writes never reach the activity-log trigger.
- `tasks_z3_assign_creation_metadata` trigger — after the existing archive guard has locked the stored parent event, it takes the transaction advisory lock, replaces authenticated input with `created_by = auth.uid()`, and assigns `max(sort_order) + 1024` in the initial event/phase/status lane. Migration-owner fixtures with no JWT may retain an explicit creator or fall back to the event creator; authenticated callers cannot use that path.
- `tasks_validate_dependency` trigger — fixed-empty-path `SECURITY DEFINER` and explicitly VOLATILE. It derives the event from stored row state, takes the event advisory lock in one statement, then checks self/same-event/cycle rules in later statements so `READ COMMITTED` receives a fresh graph snapshot after waiting.
- `tasks_guard_referenced_prerequisite_deletion` trigger — rejects direct deletion of a referenced prerequisite with SQLSTATE `CCD01`. It permits the existing nested whole-event deletion path identified by `pg_trigger_depth() > 1`, so event cascade deletion can remove a dependency chain together.
- `tasks_z0_reject_event_id_changes`, `tasks_z1_reject_created_by_changes`, and `tasks_z2_set_destination_lane_order` — later-alphabetical `BEFORE UPDATE` guards that run after the archive and assignee guards. Real task reparenting and creator changes always fail. The z2 trigger is `SECURITY INVOKER`: raw same-lane rank changes fail, while raw phase/status changes take the shared advisory lock and use restricted definer helpers so RLS-hidden rows cannot produce a duplicate rank or bypass the dependency gate. Every raw forward status change now requires its proposed prerequisite to be Completed; backward and same-status updates remain unblocked. The postgres-owned narrow-writer context returns before this raw gate, leaving `move_task()` to enforce its identical rule internally. The older deferred event-move invariant trigger remains attached as defense in depth.
- `task_work_links_guard_writes` trigger — locks the referenced task `FOR NO KEY UPDATE`, then its stored parent event `FOR SHARE`, and revalidates both before insert/delete. The task lock serializes the 20-link cap. Archived parents reject both operations. An FK-cascade delete is allowed only at nested trigger depth after the existing task guard has already approved the task deletion; Archived task deletion is rejected before that cascade begins.
- `task_work_links_reject_updates` trigger — rejects every work-link update except the FK-driven transition of `created_by` from a value to null while every other column stays identical. This preserves `ON DELETE SET NULL` without creating a general update path or allowing `task_id` changes.
- `task_volunteers_guard_writes` trigger — uses the child-specific task-row then event-row order, revalidates stored parentage, rejects inserts outside Active events, freezes every child write under Archived parents with `CCB08`, and rejects every update (including `task_id`) with `CCB09`. Nested task-FK cascades are allowed only after the task's own guard has approved deletion.
- `events_set_updated_at` trigger on `events` — assigns a monotonic value based on `clock_timestamp()` before every event update. The edit RPC always updates the event row, including task-only saves, so every successful edit advances the concurrency token.
- `events_guard_banner_url` trigger on `events` — permits a null banner or a Supabase public banner URL for that event's own `<event_id>/<uuid>.webp` object, and verifies the object already exists through a fixed-search-path security-definer helper. This closes direct insert/update paths that could otherwise store arbitrary URLs.
- `events_require_task_when_inserted_active` / `tasks_preserve_active_event_task_on_delete` / `tasks_preserve_active_event_task_on_event_move` — deferred constraint triggers that enforce at transaction end that a newly inserted Active event and an Active event affected by task deletion or a real `event_id` change retain at least one task. They do not fire for ordinary event/task updates; Drafts may remain empty, same-transaction replacements work, and event deletion remains compatible.
- Known, accepted limitation: the raw `tasks` row is not field-masked at the column-grant level. A confidential raw row is available only to an active Admin, active owning Co-Admin, or active non-Draft primary/assist assignee. Restricted RPCs—not raw `SELECT`—serve allowed viewers and any future archive late-share viewers. Permanent direct-`SELECT` regression tests guard this boundary.

## Storage

Bucket `avatars`: public read, 2 MB limit, MIME types `image/jpeg`, `image/png`, `image/webp`. Files live at `<user_id>/avatar.webp` (one fixed filename, so re-uploading overwrites). Storage RLS: anyone can read; a user can insert/update/delete only inside the folder named after their own `auth.uid()`. **The bucket itself is not created by migrations** — create it by hand in each environment; the migration only creates the policies.

Bucket `banners`: public read, 2 MB limit, MIME types `image/jpeg`, `image/png`, `image/webp`; it is created by the Step 7 migration. Saved app files live at `<event_id>/<random_uuid>.webp`. Storage writes require an active Admin or Co-Admin and an existing Draft or Active event matching the first folder segment. Missing/malformed events, Members, inactive users, and Archived events fail closed. Replacements use a new filename, update `events.banner_url` first, and only then delete the former object.

Known Storage limitation: Postgres and Storage cannot share a transaction. Directly deleting a Draft event, an archive race between upload and URL save, or a Storage outage during post-update cleanup can leave an unreferenced banner object. Cleanup never bypasses the Archived-event freeze.

## How to test an RLS policy (simulate a logged-in user in the SQL Editor)

```sql
set local role authenticated;
select set_config('request.jwt.claims',
  json_build_object('sub', '<user-uuid>')::text, true);
select * from events;  -- now filtered exactly as that user would see it
```

Running queries as the default `postgres` role bypasses RLS and proves nothing.
